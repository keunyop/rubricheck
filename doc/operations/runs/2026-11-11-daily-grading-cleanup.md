## 평가 실패와 삭제

- 인증된 production 관리자 API에서 이전에 분류한 루브릭 구조화 실패만 남아 있고 신규 항목은 없음을 확인했다. 같은 게스트 방문 흐름의 후속 평가 결과 생성으로 회복됐다는 이전 first-party 대조가 있다. 앞서 대조하지 못한 항목도 발생 직후 같은 방문 흐름에서 별도 시도 결과 생성이 관측됨을 오늘 확인했다.
- 이전 원본 조사에서 배점 합계 충돌 또는 행별 배점 누락이 확인됐고, 2026-11-10에 사용자 안내를 보강했다. 후속 결과 생성은 해당 방문 흐름의 전달 회복 근거이며 원래 기준표의 정확성이나 향후 재발 방지의 증명은 아니다.
- 사용자의 명시적 요청에 따라 조회한 기존 항목 집합이 바뀌지 않았음을 검사한 뒤, 관리자 API의 ID별 `DELETE`로 각 기록과 보관 원본을 삭제했다. 재조회 결과 목록은 비어 있다. 이는 진단 이력 정리이며 평가 정책이나 점수를 변경하지 않았다.
- 삭제된 원본은 복구할 수 없다. 필요한 원인 요약은 이전 비공개 분석과 본 실행 기록에 식별자 없이 남겼다. 새로운 구조화 실패가 생기면 다음 daily에 새 항목과 후속 성공을 다시 대조한다.

## 일일 점검

- Supabase first-party의 이전 관리자 점검 이후 terminal attempt를 집계했다. 수집 범위에서 새 server terminal 실패는 관측되지 않았고, 성공·validation·access는 구분했다. 별도 network 이벤트는 attempt 분모에 넣지 않았다. 동의/방문자 수집 범위에 한정되며 전체 production 실패율은 아니다.
- 관리자 피드백에는 기존에 답변 완료한 항목만 있고 새 항목이 없다. first-party 결제 웹훅 실패도 새로 관측되지 않았다. Stripe live 최근 charge 목록에서 점검 시작 이후 새 charge가 없었다. checkout 시작만으로 결제 실패나 성공을 판정하지 않았다.
- Vercel의 최근 24시간 평가 route 오류 cluster는 없었다. 개별 runtime log 24시간 조회는 요금제 보존 기간 제한으로 실패하여 로그 부재로 해석하지 않았다.
- 집계의 기간·분모·원천 시각과 제한은 Git 제외 비공개 owner 기록에 보관한다. Supabase가 반환한 `now()`와 운영 시계가 약 한 시간 달라 조회 종료 시각을 임의 보정하지 않았다.
