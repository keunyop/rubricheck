# 제품 발견, 활성화, 실험

`discover`·`experiment` 또는 weekly/monthly에서 해당 판단이 필요할 때 읽는다. 기존 [backlog](../../../../doc/operations/backlog.md)와 [실험 기록](../../../../doc/operations/experiments.md)을 사용한다. 별도 작업 큐나 고객 문서 저장소를 만들지 않는다. 세부 판단은 해당 실행 기록에 남기고 같은 작업 ID로 연결한다.

## 문제와 기능 요청 구분

기능을 고르기 전에 대상 사용자, 달성하려는 일, 현재 막히는 단계, 근거의 날짜·출처를 적는다. 관측 사실·사용자 주장·PO의 추론을 구분한다. 동일 사용자의 반복 문의는 독립 수요 여러 건으로 세지 않는다. 인터뷰나 사용자를 가상으로 만들어 근거로 삼지 않는다.

목표 결과 → 해결할 고객 문제 → 가능한 해결책 → 검증 방법 순으로 좁힌다. 예를 들어 “재평가 버튼 추가”는 해결책이고, “첫 결과를 본 사용자가 수정한 초안을 다시 평가하는 경로를 찾지 못함”은 확인할 문제다. 실제 근거가 없다면 가설로 표시한다.

다음 대안을 비교하되 이미 정해진 사용자 범위를 임의로 확대하지 않는다.

- 현재 유지: 빈도·영향이 작거나 더 중요한 문제가 있는가?
- 기존 기능·문구·샘플·도움말로 해결: 사용자가 기능을 발견하지 못하는 문제인가?
- 작은 동작 변경: 어느 단계 하나를 바꾸면 가설을 검증할 수 있는가?

선택 이유와 보류 이유를 남긴다. 실행 권한 안의 가역적 선택은 근거에 따라 진행하고, 현재 자료로 해결할 수 없는 핵심 판단만 사용자에게 묻는다. 큰 기능 확장이 유일한 답이라고 가정하지 않는다.

## 위험 가정과 최소 요구사항

유용성(실제 과제를 해결하는가), 사용성(사용자가 실행할 수 있는가), 사업성(비용·지원 부담을 감당하는가), 구현 가능성(현재 시스템으로 가능한가)을 살핀다. 결론을 뒤집을 수 있는 가정부터 검증한다. 각 핵심 가정에는 현재 근거, 틀렸음을 보여줄 관측, 가장 싼 확인 방법을 붙인다. 정보가 없으면 낮은 확신으로 표시하며 임의 숫자로 점수를 정밀하게 꾸미지 않는다.

여러 동작·화면을 바꾸는 기능은 기존 backlog/실행 기록에 다음 결정 요약을 남긴다. 단순 수정은 필요한 항목만 쓴다.

| 항목 | Rubricheck에서 결정할 것 |
| --- | --- |
| 사용자와 문제 | 어떤 상황에서 어떤 평가 과제를 끝내지 못하는가; 근거와 미확인 가정 |
| 목표와 측정 | 첫 성공·재사용 등 바꿀 행동, 기준선과 관측 기간; 실제 이벤트 존재 여부 |
| 선택과 범위 | 기존 기능/무개발 대안과 비교한 최소 변경, 이번에 포함하지 않을 기능 |
| 수용 기준 | 사용자 행동과 관측 가능한 결과; 관련된 정상·실패·복구 경우 |
| 제약과 검증 | 평가 정확성·원본 보존·중복 차감·지연·비용 중 영향받는 항목 |
| 출시와 후속 판단 | 권한, 복구 방법, 책임 작업 ID, 확인일과 채택/중단 기준 |

기능 목록의 완료와 사용자 결과의 개선을 따로 판단한다. 요청 수만으로 로드맵을 정하지 않고 목표 결과·근거·구현 및 유지 비용을 함께 비교한다.

## 첫 성공과 재사용

현재 코드와 [지표 정의](measurement.md)에서 실제 흐름·이벤트를 확인한다. 분석할 흐름의 예는 유입 → 평가 시작 → 입력/루브릭 준비 → 평가 완료 → 결과 확인 → 후속 평가다. 이 예를 실제 이벤트명이나 모든 사용자의 필수 순서로 간주하지 않는다.

가입·CTA 클릭·서버 성공 응답을 곧바로 사용자 가치 달성으로 취급하지 않는다. “사용 가능한 평가 결과를 확인함”을 첫 성공 후보로 삼고, 실제 관측 가능한 이벤트로 정의한다. 결과 열람을 측정하지 못하면 서버 완료는 대리지표라고 표시한다. 중복 요청·실패 후 재시도는 재사용과 구분한다.

전환율은 단계별 고유 사용자/세션/요청 중 어떤 단위인지, 진입 분모, 관측 창을 명시한다. 단계 이탈과 첫 결과까지 걸린 시간을 보고 가장 큰 마찰 하나를 고른다. 입력 예시, 오류 복구, 다음 행동 안내처럼 현재 흐름의 작은 개선부터 검토한다. 필요한 루브릭 검증이나 사용자 동의를 없애 전환율을 올리지 않는다.

재사용 분석은 첫 성공 시점 또는 가입 시점이 같은 cohort를 비교한다. 관측 창이 끝난 집단만 유지율 분모에 넣고 최근 집단은 관찰 중으로 분리한다. 활성화 행동을 관측하는 창과 이후 재사용을 판단하는 창을 겹치지 않게 정한다. 초기에 특정 행동을 한 사용자들의 유지율이 높더라도 그 행동을 강제하면 유지율이 오른다고 단정하지 않는다.

## 작은 실험과 판정

실험 시작 전에 같은 작업 ID로 다음을 기록한다.

- 가설: 어떤 관측 때문에, 누구에게, 무엇을 바꾸면, 어떤 행동이 달라질 것으로 보는가.
- 설계: 비교 대상, 기준선의 기간·분모, 핵심 변화 하나, 실제 노출/배포 시작 시각.
- 판정: 주 지표 하나, 의미 있는 개선 기준, 관측 기간/필요 표본, 결과 확인일.
- 보호 지표: 영향받는 평가 품질·실패율·중복 차감·지연·비용의 허용 범위와 복구 조건.
- 실행 범위: 비용·권한, 실행 가능한 최소 방법, 접근·측정 공백.

트래픽과 기준선으로 필요한 표본을 확보할 수 있는지 먼저 판단한다. 가능하면 배정 단위·고정 노출·표본 규모의 근거·분석/종료 규칙을 정하고 계측부터 검증한다. 유리한 중간 결과만 보고 조기 종료하지 않는다. 품질·비용 등의 중단 조건 위반은 예정일 전에도 복구 사유다.

저표본이면 합성 자료를 이용한 사용 흐름 점검, 허용된 기존 피드백 분석, 작은 프로토타입이나 전후 관찰로 가장 큰 불확실성을 줄인다. 합성 자료는 실제 고객 수요 증거가 아니며 전후 관찰은 인과 효과를 입증하지 못한다. 통계적으로 판정할 수 없으면 “판정 불가”로 남기고 관측/계측 개선 또는 새 가설을 정한다. 유의하지 않다는 이유만으로 효과가 없다고 결론 내리지 않는다.

결과는 채택·수정 후 재검증·중단·판정 불가 중 하나로 기록하고, 분모·효과 크기·불확실성·보호 지표를 함께 적는다. 가격·무료 한도·환불·외부 연락 권한은 기존 원장을 따른다. 실험이라는 이유로 권한을 넓히지 않는다.

## 회고와 다음 실행

기한이 된 실험부터 예상과 관측, 데이터 한계, 계속/중단 이유를 대조한다. [실험 기록](../../../../doc/operations/experiments.md)의 같은 항목과 backlog를 갱신하고 다음 확인일을 state에 연결한다. 실제 배포 전에는 성과 관측 시계를 시작하지 않는다.

반복해서 확인된 작업 실패는 가장 효과적인 위치에 해결책을 둔다. 구현 불변조건은 코드·타입·검증으로, 판단 절차는 해당 스킬 참고 문서로 반영한다. 일회성 사건을 모든 운영 작업의 새 의무로 만들지 않는다.
