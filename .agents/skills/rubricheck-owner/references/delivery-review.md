# 변경 영향과 완료 증거

`review`, 동작 변경, 품질·비용·성능 개선에 적용한다. 기존 [출시 절차](journal-and-release.md)의 권한·배포 기준을 대체하지 않는다. 검토 요청만 받은 경우 검토 결과를 제공하고 구현·출시까지 자동으로 확대하지 않는다.

## 문제를 재현하고 영향 범위 좁히기

현재 증상과 기대 행동을 먼저 적고 코드·기존 이력에서 현재 동작의 이유를 확인한다. 이미 있는 helper, 데이터 계약, 테스트 경로를 재사용한다. 근거가 없는 설계 의도를 사실로 적지 않는다.

변경이 영향을 주는 호출자뿐 아니라 API 응답 형태, 저장 데이터, 재시도, 중복 이벤트, 캐시, 이전 결과 열람처럼 경계를 건너는 소비자를 확인한다. 관련 없는 모든 경계를 체크리스트로 검사하지 않는다.

안전성을 좌우하는 핵심 조건을 골라 실제 경로로 검증한다. 예: “같은 평가 요청을 재시도해도 사용량은 한 번만 차감된다”, “표시 수정은 저장된 평가 원본을 덮어쓰지 않는다”. 조건의 증거를 코드 확인·자동 테스트·실행 중 앱 확인으로 구분하고, 실행하지 못한 부분은 미검증으로 남긴다.

성능 개선은 동일 입력·설정·환경에서 변경 전후를 비교한다. 캐시·동시성·실패율 때문에 빨라 보인 것은 아닌지 확인하고, 특정 함수의 개선과 사용자가 결과를 받는 전체 시간을 구분한다. 측정이 없는 경우 성능 향상을 단정하지 않는다.

## 두 관점으로 검토

1. 요구사항: 요청된 행동과 수용 기준을 충족하는가? 누락한 실패·복구 경로 또는 불필요한 기능이 있는가?
2. 정확성: 영향받는 경계와 불변조건을 지키는가? 증상만 숨겼거나 평가 품질·비용·데이터 보존을 악화시키지 않는가?

기존 위임 범위에서 별도 검토자를 쓸 수 있으면 변경과 수용 기준·원자료를 전달한다. 작성자의 결론을 검토 결과로 재사용하지 않는다. 순차 수행 시에도 두 관점을 구분한다. 하위 에이전트의 “완료” 보고만으로 통과시키지 않는다.

발견 사항에는 사용자 영향, 발생 조건, 위치, 검증 증거를 붙인다. 재현된 결함과 코드로 확인한 결함, 아직 입증하지 못한 위험을 구분한다. 실행하지 못한 보안·데이터 손실 우려를 무조건 삭제하지 않고 필요한 확인을 명시한다. 검토 자체가 새로운 유료 모델이나 대량 실행의 근거가 되지 않는다.

## 사용자 흐름 확인

UI/평가 동작 변경은 가능한 로컬·preview에서 합성 또는 허용된 자료로 진입 → 입력 → 실행 → 결과 → 복구/다음 행동까지 영향받는 흐름을 확인한다. 모바일·키보드·빈 상태·로딩·오류 상태는 변경과 관련된 것만 확인한다. 스크린샷만으로 API 응답·저장·차감이 맞다고 판정하지 않는다.

실제 결제, 외부 전송, 과금 모델 호출이 필요한 경우 기존 승인과 테스트 환경을 확인한다. 접근할 수 없는 검증은 남겨 두고 가능한 정적/로컬 검증까지 완료한다. 시험 경로를 통과했다고 production까지 확인했다고 쓰지 않는다.

## 완료 판정

검증마다 대상 변경/버전, 실행 명령 또는 조작, 기대 결과와 실제 결과, 실행 환경, 남은 한계를 기록한다. 변경 후 관련 검증 결과가 있어야 완료를 주장한다. 검증 이후 관련 코드가 바뀌면 영향을 받는 검증만 다시 수행한다.

스킬·문서만 수정했다면 frontmatter·연결 경로·지침 충돌과 실제 요청에 대한 적용 가능성을 검토한다. 그 검토로 앱 동작이나 출시 후 사용자 성과가 검증됐다고 쓰지 않는다. 회귀 위험이 있는 버그는 재현/회귀 테스트를 사용하고, 가역적인 작은 문구 수정에 구현을 따라 쓰는 테스트를 추가하지 않는다.

최종 결과는 충족한 수용 기준, 확인한 결함/미검증 위험, 실행한 검증, 출시 준비 상태, 다음 행동으로 정리한다. `implemented`부터 `verified_production`까지의 상태 구분은 본문을 따른다.
